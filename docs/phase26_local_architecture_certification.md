# Phase 26 — Local architecture-release evidence workflow

## Purpose

The repository does **not** need a `.github` directory or GitHub Actions to
complete architecture release review. This phase adds one local command that
runs the existing external-backend BMI acceptance test and an actual two-worker
`spawn` portability test for the host operating system, then checks the reports
against the Phase 25 release gate. It is orchestration only: no model equations,
random draws, result formats, public BMI variables, or checkpoint schemas change.

The command is available on Windows and Linux. **It does not pretend that a
Windows run proves Linux compatibility**, or vice versa. Official `bmipy`
abstract-method checking is enabled by default and is required for a report to
qualify for release review. Both platforms must use the same selection JSON,
startup JSON, scientific YAML, external factory entrypoint, and scientific input
contents. The backend must be an independently implemented, file-backed annual
model; the bundled reference backend is an interface demonstration only.

## Collect evidence without hosted CI

Install the optional requirements in the relevant environment:

```bash
python -m pip install -e ".[bmi]"
```

Prepare a **schema version 1**, single-scenario `selection.json` with
`backend: external`, an importable `external_factory`, and a startup manifest
without a replay file. Pass each backend-specific scientific data file with
`--input-file` (paths relative to the selection JSON). Run on **Windows**:

```bash
python -m src.interfaces.bmi.local_certification selection.json evidence --input-file backend_domain.json --n-scenarios 2 --n-jobs 2
```

It writes `evidence/acceptance.json` and `evidence/windows.json` only after
acceptance, serial, spawned-process, and resume checks succeed. The first
platform will return `pending_evidence` until the other platform is checked.

Copy the same project configuration and scientific inputs to **Linux**, copy
`windows.json` into the Linux `evidence` directory, then run the **same** command.
That creates `evidence/linux.json` and checks that all evidence refers to the
same configuration and backend. (The reports are portable: SHA-256 identity
hashes exclude machine-specific absolute scientific input paths.) Alternatively,
collect the reports separately and combine them afterward.

Run the existing release gate using all three files:

```bash
python -m src.interfaces.bmi.release_gate --acceptance evidence/acceptance.json --windows evidence/windows.json --linux evidence/linux.json --report evidence/readiness.json --require-ready
```

A complete result is `ready_for_architecture_release_review`, **not** CSDMS
certification or scientific validation of the external model. Reviewers must
corroborate the unsigned JSON reports and platform runs independently.

## Diagnostic runs and safeguards

`--without-bmipy` runs the process checks without the official BMI check, but
reports `pending_official_bmipy` and **cannot** qualify for the release gate.
Use it only for diagnosing multiprocessing or environment issues.

The command refuses a native selection, replay startup, non-supported operating
system, unlisted backend asset, or a zero/one-worker "parallel" run. If scientific
inputs change or spawned workers fail, existing evidence files remain unchanged.
Before writing, it checks the new acceptance and portability reports against
the external model source, scientific content identity, and any existing
opposite-OS report, rejecting stale or incompatible reports. Files are
atomically replaced individually after validation, not as one transactional
multi-file commit; an unexpected OS crash between writes can still leave a
partial bundle, which the release gate must validate again.

For a small scientific case, the two-worker execution can still be expensive;
this command intentionally does **not** substitute mocked workers for release
evidence. The ordinary unit tests mock the collection orchestration, while the
actual certificate must be generated by running the selected model on each host.

## Scope of remaining work

- Collect **real** Windows and Linux reports with `bmipy` installed.
- Review their consistency, the backend's actual scientific comparability and
  any integration failures; independently corroborate report provenance.
- Check whether untracked backend assets, transitive Python dependency versions,
  and native diagnostic gaps need additional policy or tests before release.

The absence of a `.github` directory is an intentional repository choice, not a
blocker to local architecture review. This phase adds no hosted-CI files or
requirements to commit that directory.
